This document defines the release channels, signing requirements, packaging models, and public distribution policies for **Ornare V1**.

## 2. Channel A: Microsoft Store (Primary)

### 2.1 Ingestion & Signing Architecture
- Under Microsoft Store policy, developers submit their `.msix` or `.msixbundle` packages to Partner Center.
- During ingestion and certification, **Microsoft replaces the developer's development signature with an official Microsoft-trusted Store signature**.
- **Crucial Rule:** Lack of an external commercial CA code-signing certificate (EV/OV) is **NOT a blocker** for Microsoft Store submission. Self-signed or unsigned candidate packages generated by Visual Studio / MSBuild are accepted by Partner Center.

## 3. Channel B: Direct Vellium Website Distribution (Secondary)

### 3.1 Direct Sideloading & Web Distribution Model
For users downloading Ornare directly from the Vellium website (`vellium.com`) as a standalone `.msix` or `.appinstaller` file, Windows App Installer enforces strict trust verification:
- The package **must be digitally signed** using a code-signing certificate issued by a public Certificate Authority (CA) in the Windows Root Certificate Program (e.g., DigiCert, Sectigo, GlobalSign, or Azure Trusted Signing).
- The signature must include a valid RFC 3161 timestamp to remain valid after certificate expiry.
- Without a CA-trusted signature, Windows SmartScreen will aggressively block installation with `0x800B0109` (*A certificate chain processed, but terminated in a root certificate which is not trusted by the trust provider*).
- Initial downloads will trigger SmartScreen reputation warnings until sufficient install volume and reputation are built.

### 3.2 Channel B Readiness Status
- **Status:** **BLOCKED**
- **Reason:** A commercial code-signing certificate or Azure Trusted Signing identity has not yet been provisioned for the Vellium domain.
- **Independence:** This blocker is strictly isolated to Channel B and does **not** block Microsoft Store readiness.

## 4. Multi-Architecture Packaging & Bundle Architecture

### 4.1 Target Architecture Specification
Ornare V1 is designed for two native architectures on Windows 11:
1. **x64 (amd64):** Intel/AMD 64-bit architecture.
2. **ARM64 (aarch64):** Qualcomm Snapdragon X Elite / Copilot+ PCs and native Windows on ARM hardware.

### 4.2 Bundle Composition Rules
- An `.msixbundle` combines individual architecture packages (`Ornare_1.0.0.0_x64.msix` and `Ornare_1.0.0.0_arm64.msix`).
- When a user installs the bundle via Microsoft Store or App Installer, Windows automatically downloads only the architecture-matched package for the host device.
- **Non-Negotiable Architecture Invariant:** An ARM64 package **must contain pure native ARM64 binaries** (`Ornare.ShellExtension.dll` ARM64 + `Ornare.App.exe` ARM64). Mixing x64 or x86 binaries in an ARM64 package under emulation is strictly forbidden.

### 4.3 Current Architecture Status
- **x64 Native Build:** **VERIFIED** (Native C++ shell extension + managed .NET 10).
- **ARM64 Managed Build:** **VERIFIED** (.NET 10 compilation for `win-arm64`).
- **ARM64 Native Shell Build:** **NOT PROVEN** (`Microsoft.VisualStudio.Component.VC.Tools.ARM64` not installed on host machine; requires elevation).
- **ARM64 Runtime Execution:** **NOT PROVEN** (No physical ARM64 hardware connected).
- **MSIXBundle Status:** **DEFERRED** pending native ARM64 C++ compilation.

## 5. Scope Management Policy (Section 12)

If native ARM64 qualification cannot be completed prior to the desired public launch date:
1. **Original V1 Specification (Default):** Full public release remains **BLOCKED** until ARM64 hardware qualification is satisfied.
2. **x64-Only Initial Release (Option B):** Requires formal, written approval from the Product Owner to amend the V1 scope to an x64-only initial launch, deferring ARM64 to V1.1. Under no circumstances may an agent reduce scope unilaterally.
